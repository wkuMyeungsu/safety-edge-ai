개발·시험·배포 협업 방법

누가 어디를 고치는지, 집 밖에서 실제 Pi로 사진을 보내 시험하는 방법, PR·CI를 거쳐 Pi에 올리는 방법을 모았다. 시스템 구조는 architecture.html에 있고, 규칙의 원본은 저장소 루트의 CLAUDE.md·README.md다.

  • 라즈베리 파이 실물은 명수가 가지고 있다. 배포·재빌드는 누구나 deploy-pi로 한다. 설치, 모델 파일 교체, .env 변경, 실측은 명수에게 요청한다.
  • 담당이 바뀌면 README의 "폴더별 담당" 표와 .github/CODEOWNERS만 고친다. 폴더 구조와 파트 이름은 바꾸지 않는다.
Remote test

집 밖에서 실제 Pi로 보내기 (Tailscale Funnel)

Pi는 명수 집에 한 대뿐이다. 다른 곳의 ESP32나 PC에서도 실제 처리 흐름(gateway → inference → uploader → Supabase)으로 사진을 보낼 수 있도록, gateway(8001)만 Tailscale Funnel의 HTTPS 주소로 인터넷에 열어 두었다. SSH 같은 다른 포트는 열지 않는다.

같은 네트워크 (명수 집)인터넷 (다른 곳)
주소http://<Pi IP>:8001/framehttps://<Pi 이름>.<tailnet>.ts.net/frame
토큰없음X-Device-Token 필수 (팀 공용)
ESP32 코드HTTPClient.begin(url)WiFiClientSecure + HTTPClient.begin(client, url)
토큰이 틀리면-401. Pi .env의 GATEWAY_TOKEN이 비어 있을 때도 모두 401
 
# PC에서 시험 사진 한 장 (장치 ID는 test-로 시작해 나중에 골라 지운다)
curl -H "X-Device-Id: test-<이름>" -H "X-Device-Token: <토큰>" -H "Content-Type: image/jpeg" \
     --data-binary @사진.jpg https://<Pi 이름>.<tailnet>.ts.net/frame
# → 202 {"status": "queued", "queue": 1, "frame": "ab12cd34"}

# 판정 결과 보기 (최근 50건, gateway를 다시 시작하면 비워진다)
curl "https://<Pi 이름>.<tailnet>.ts.net/recent?device_id=test-<이름>"
  • 실제 주소와 엔드포인트별 응답은 api-manual.html, 요청 형식은 contracts/frame.md에 있다.
  • gateway는 요청에 프록시가 붙이는 헤더(X-Forwarded-For, Forwarded, Cf-Connecting-Ip, Tailscale-Funnel-Request)가 있으면 인터넷에서 온 요청으로 보고 토큰을 검사한다.
  • 토큰은 Pi의 pi/.env와 각자의 config.h에만 둔다. 커밋하지 않고, 팀원에게는 개인 메시지로 전하며, 로그에도 찍지 않는다.
  • 장치 ID 규칙: 각자의 ESP32는 cam-<이름>, curl·pytest 같은 시험은 test-<아무거나>를 쓴다. 시험 기록은 test-로 골라 지울 수 있다.
  • 검토했지만 쓰지 않은 방법: 공유기 포트포워딩, Cloudflare Tunnel(도메인 필요), ngrok 무료(월 1GB 제한), 팀원 SSH. 이유는 decisions.md에 있다.
Deploy

내 브랜치를 실제 Pi에 올려 시험하기 (deploy-pi)

  1. GitHubActions → deploy-pi → Run workflow를 누르고 ref(올릴 브랜치, 기본 dev)와 action을 고른다. 저장소에 write 권한이 있는 팀원은 누구나 실행할 수 있다.
  2. deployPi에 설치된 self-hosted runner(rpi5, 라벨 pi)가 그 브랜치를 받아 docker compose up --build를 실행하고, 컨테이너가 healthy가 될 때까지 기다린다. 시작 로그에 commit=이 찍힌다.
  3. 시험 중배포가 끝나면 hold_minutes(기본 30분) 동안 "시험 중"으로 표시되어 다른 사람의 deploy가 막힌다. 표시를 건 본인은 막히지 않으니 고쳐서 다시 올리면 된다.
  4. 확인실행의 마지막 단계 "상태·최근 로그"에서 지금 Pi에 올라간 커밋, 시험 중인 사람, docker compose ps, /health, 최근 로그 80줄을 본다. 바꾸지 않고 상태만 보려면 status를 고른다.
  5. release시험이 끝나면 올린 사람이 release를 누르고 dev를 다시 올려 둔다. 누르지 않아도 시간이 지나면 표시는 저절로 풀린다.
  • 막히면 기다리지 않고 바로 실패하며, 이유는 실행 화면 맨 위 Summary에 남는다. 예: MOTNV 님이 feature/pi/x (abc1234)를 시험 중이라 멈춤 (15:05까지). 이럴 때는 그 사람에게 확인한 뒤 release하고 다시 deploy한다.
  • 모델 파일(pi/models/*.onnx)과 .env는 git 밖에 있어서 배포로 바뀌지 않는다. 바꿀 일이 있으면 명수에게 요청한다.
  • public 저장소라 실행 로그는 누구나 볼 수 있다. 비밀값을 로그에 찍지 않는다.
  • 명수가 Pi에서 직접 작업할 때도 같은 규칙을 쓴다(pi-deploy status · hold · deploy · release). 다른 사람이 시험 중이면 직접 실행하는 docker compose up 등도 막힌다. 설치 방법과 자세한 내용은 pi/README.md의 "Pi 배포"에 있다.
Debug

사진 한 장 따라가기

  1. ESP32 / curl202 응답 본문의 frame(사진 번호, 8자리 hex)을 확인한다. ESP32는 응답 본문을 시리얼에 그대로 찍는다.
  2. gateway/recent?device_id=…에서 verdict, upload와 구간별 시간(wait_ms·infer_ms·upload_ms·total_ms)을 본다.
  3. Pi 로그docker compose logs --no-color | grep frame=<번호>로 찾는다. gateway의 "처리 끝" 줄과 uploader의 "저장 성공 … log_id=" 줄이 같은 번호로 이어진다. deploy-pi의 status로도 최근 로그를 볼 수 있다.
  4. Supabaseuploader 로그의 log_id로 safety_logs 행을 찾는다. 웹에 위반이 안 뜰 때 확인하는 순서는 cloud/README.md의 "로그 보는 곳"에 있다.
  • 로그 한 줄 형식은 시각 레벨 로거 파일:줄 메시지 key=value…이다. 로거 이름은 pi.gateway·pi.inference·pi.uploader이고, 시각은 한국 시각으로 찍힌다.
  • 자세히 볼 때만 LOG_LEVEL=DEBUG로 올린다. 로그는 서비스당 10MB 파일 3개까지만 남는다.
Branch · PR

브랜치에서 병합까지

  1. 브랜치dev를 최신으로 받고 거기서 <태그>/<파트>/<기능> 브랜치를 만든다. 태그는 feature fix docs refactor chore 중 하나다. 파트는 고치는 폴더의 최상위 이름(esp32 pi cloud web)이고, 여러 파트에 걸치면 common을 쓴다. 예를 들어 pi/uploader/를 고치면 담당이 cloud여도 feature/pi/…다.
  2. 커밋메시지는 <타입>(<파트>): <요약> 형식이고, 타입은 feat fix docs refactor chore 중 하나다. 계약을 바꾸는 커밋에는 [contract]를 붙인다. 예: feat(pi): gateway 대기 줄 추가
  3. PRdev로 올린다. main(최종본)과 dev(통합)에는 직접 push하지 않는다.
  4. CIci-ok가 초록불이어야 병합할 수 있다. 실패하면 테스트를 지우거나 건너뛰게 만들지 말고 원인을 고친다.
  5. 병합병합 방식은 Create a merge commit만 쓴다. 앞 PR의 CI가 끝난 뒤 하나씩 병합한다. GitHub 쪽 브랜치는 자동으로 지워지고, 내 PC의 브랜치는 git switch dev && git pull --prune 뒤 git branch -d <브랜치>로 지운다.
  • 실수로 로컬 dev에 커밋했다면 git switch -c <작업 브랜치>로 옮긴 뒤 git branch -f dev origin/dev로 되돌린다.
  • git pull 뒤에는 docker compose up --build로 다시 빌드한다. --build가 없으면 예전 이미지가 그대로 돈다.

CI: 바뀐 파트만, PR에서만

job언제 도는가하는 일
lint항상ruff (수 초)
pipi/·tests/pi/·tests/e2e/arm64 러너에서 compose 빌드(캐시) → healthcheck 통과까지 기동 → pytest tests/pi tests/e2e tests/contracts. ONNX는 Release model-v1에서 받아 캐시한다

ci-ok항상 (마지막)위 job이 모두 통과했거나 건너뛰었으면 초록. 브랜치 보호에 걸린 유일한 필수 검사다
  • docs/contracts/·tests/contracts/가 바뀌거나 dev → main PR이면 모든 job이 돈다.
  • 트리거는 pull_request뿐이고, 같은 PR에 새 커밋이 오면 이전 실행을 취소한다. 지난 프로젝트에서 CI 시간이 2분에서 8분으로 늘었던 일을 피하려는 설정이다.
  • CI를 느리게 만드는 변경(무거운 빌드·다운로드 추가)은 캐시 설정을 같은 PR에 넣는다.
  • 개발 환경 값(ESP32 FQBN·코어 버전, Python 이미지)을 바꾸면 ci.yml과 CLAUDE.md의 표를 같은 PR에서 함께 고치고, PR 설명에 "환경 갱신 필요"를 적는다.
Tests

테스트 쓰고 내 PC에서 돌리기

# 저장소 루트에서. 내부 포트(8003·8004)도 열어 주는 CI용 설정을 겹친다
cd pi
docker compose -f docker-compose.yml -f docker-compose.ci.yml up -d --build --wait
cd ..
pip install -r tests/requirements.txt
pytest tests/pi tests/e2e -m "not pi and not supabase"
  • tests/<파트>/test_*.py로 넣으면 CI 파일을 고치지 않아도 CI에서 돈다.
  • 서비스 코드를 import하지 말고 HTTP로 부른다. 주소는 conftest.py의 fixture(gateway_url 등)를 쓴다.
  • 판정은 문자열이 아니라 응답 코드, JSON 필드, 출처로 한다.
  • 마커: 모델이 필요하면 model, Supabase가 필요하면 supabase, Pi에서만 의미 있는 측정이면 pi를 붙인다.
  • 시험이 끝나면 pi/buffer/에 쌓인 시험 기록을 지운다. 그대로 두면 나중에 .env를 넣었을 때 Supabase로 올라간다.
Contracts

파트 사이 형식 바꾸기

  1. 먼저 문서구현하기 전에 docs/contracts/에 형식을 적는다. 보내는 쪽과 받는 쪽 담당자가 둘 다 확인하면 문서 상태를 "합의"로 바꾼다.
  2. 커밋계약을 바꾸는 커밋 메시지에는 [contract]를 붙인다. 이 경로가 바뀌면 CI가 모든 파트를 검사한다.
  3. 배포 순서받는 쪽부터 올린다: Supabase 스키마 → pi → web → esp32. 새 필드는 선택으로 두어, 받는 쪽이 먼저 올라가도 모르는 필드를 무시할 수 있게 한다.
  4. 상대가 없을 때가짜로 대신한다. ESP32 대신 curl로 사진 POST, Supabase 대신 uploader 버퍼, Supabase 데이터가 없으면 웹의 데모 모드를 쓴다.
Records

커밋하지 않는 것, 남겨야 하는 것

커밋하지 않는다

  • .env, esp32/firmware/safety_cam/config.h (Wi-Fi 비밀번호, 토큰, Supabase key, IP)
  • 모델 가중치 *.onnx *.pt. ONNX는 Release model-v1에 올리고 pi/models/README.md에 SHA256을 적는다
  • 영상 *.mp4 *.mov, pi/buffer/, 측정 로그 *.log
  • 예외: Edge Impulse Arduino 라이브러리 zip은 esp32/model/에 커밋한다 (CI 컴파일용)
  • Supabase service key는 Pi의 .env에만 둔다. 웹에는 anon key만 쓴다

남긴다

  • 측정한 숫자(추론 시간, 메모리, 감지율)는 어느 커밋·모델 SHA256에서 쟀는지 함께 적는다. PC·QEMU에서 잰 값을 Pi 값으로 쓰지 않는다
  • 펌웨어는 시리얼 첫 줄에 FW_VERSION을 찍고, 펌웨어를 바꿀 때마다 올린다
  • 되돌리기 어려운 결정(모델 교체, 컨테이너 추가·삭제, 계약 변경)은 선택지를 2개 이상 비교한 뒤 정하고, decisions.md에 날짜·결정·이유·버린 선택지를 남긴다
규칙이 바뀌면 원본(CLAUDE.md·README.md·pi/README.md)과 이 문서를 같은 PR에서 함께 고친다.
