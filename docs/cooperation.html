개발·시험·배포 협업 방법

내 브랜치를 실제 Pi에서 시험하고, PR과 CI를 거쳐 dev에 합치는 방법을 정리했다. 시스템 구조는 architecture.html, 규칙의 원본은 CLAUDE.md·README.md에 있다.

Access

Pi는 명수 집에 한 대뿐이다. 다른 곳에서는 사진은 Funnel로 보내고, 코드는 deploy-pi로 올린다. SSH나 그 밖의 포트는 열지 않는다.

Deploy

deploy-pi 버튼 세 개

action하는 일언제
deploy고른 브랜치를 받아 다시 빌드하고, hold_minutes(기본 30분) 동안 "시험 중"으로 표시한다내 브랜치를 실제 Pi에서 시험할 때
status바꾸지 않고 현재 커밋, 시험 중인 사람, 컨테이너 상태, 최근 로그 80줄을 보여 준다언제든
release"시험 중" 표시를 푼다시험이 끝나면 올린 사람이 누르고, dev를 다시 올려 둔다
  • 다른 사람이 시험 중이면 바로 실패하고 이유가 Summary에 남는다. 그 사람에게 확인한 뒤 진행한다.
  • 모델 파일과 .env는 배포로 바뀌지 않는다. 설치, 모델 교체, 실측은 명수에게 요청한다. 자세한 내용은 pi/README.md에 있다.

Rules

꼭 지킬 규칙

담당

  • 내 폴더와 같은 이름의 tests/만 고친다. 담당은 README의 "폴더별 담당" 표를 따른다
  • 다른 사람 폴더를 고쳐야 하면 고치지 말고 담당자에게 알린다
  • 공용 파일(docs/, README, CLAUDE.md 등)은 상의한 뒤 PR로 바꾼다

브랜치 · 커밋

  • 브랜치: <feature|fix|docs|refactor|chore>/<파트>/<기능>. 여러 파트에 걸치면 common
  • 커밋: feat(pi): 요약
  • main·dev에는 직접 push하지 않는다

CI · 테스트

  • 바뀐 파트의 job만 돌고, ci-ok 하나가 필수다
  • tests/<파트>/test_*.py에 넣고, 서비스 코드를 import하지 말고 HTTP로 부른다
  • 마커: model · supabase · pi

계약

  • 구현하기 전에 docs/contracts/에 적고 양쪽 담당이 확인한다
  • 커밋에 [contract]를 붙이면 CI가 모든 파트를 검사한다
  • 배포는 받는 쪽부터: Supabase → pi → web → esp32

커밋하지 않는다

  • .env, config.h, 토큰, key
  • *.onnx *.pt(Release model-v1에 올린다), 영상, pi/buffer/, *.log

남긴다

  • 측정한 숫자에는 커밋과 모델 SHA256을 함께 적는다. PC·QEMU 값을 Pi 값으로 쓰지 않는다
  • 큰 결정은 decisions.md에 남긴다
  • git pull 뒤에는 --build로 다시 빌드한다
# 내 PC에서 CI와 같은 테스트 (저장소 루트)
cd pi && docker compose -f docker-compose.yml -f docker-compose.ci.yml up -d --build --wait && cd ..
pip install -r tests/requirements.txt && pytest tests/pi tests/e2e -m "not pi and not supabase"
규칙이 바뀌면 원본(CLAUDE.md·README.md·pi/README.md)과 이 문서를 같은 PR에서 함께 고친다.
